# 统一向量缓存与服务器适配

本分支以官方 2.8.4 为基线，将公共向量缓存集成到 LivingMemory。
仍使用 `text-embedding-v4`，不更换 AstrBot 原生 DashScope 提供商的 ID、模型、
维度、配置对象或类型，避免仅因增加缓存而触发 FAISS 全量重建。

## 接入方式

在 LivingMemory 配置中启用 `shared_embedding_cache.enabled`，重载插件。
当前支持 DashScope 原生 `text-embedding-v4`，维度取现有提供商配置。

LivingMemory 包装匹配的 AstrBot 提供商实例，因此使用这些实例的插件、知识库
可以共享缓存。每两秒检查新增实例；插件卸载时恢复原方法。

独立客户端可连接 `http://127.0.0.1:17695/v1`：

- 模型：`text-embedding-v4`
- API Key：插件数据目录 `embedding_gateway.token` 中的本机令牌
- 可选请求头：`X-Embedding-Caller: bilibot`
- 路径：`POST /v1/embeddings`
- 输入：字符串或字符串数组（最多 128 条，单条最多 32768 字符；上游仍限制 8192 tokens）
- 返回：OpenAI 兼容浮点数组或 base64；维度必须等于配置维度

只监听本机地址。本机其他账号仍需令牌，禁止将令牌写入源码或日志。
令牌不是百炼密钥。Docker 客户端不能直接把容器 loopback 当作服务器 loopback。
硬编码上游地址、使用其他提供商实例或其他模型的调用不自动接入缓存。

## 语义与计量

同地域、同百炼账号、同模型、同维度、同缓存版本及**完全相同文本**才能复用。
不裁掉时间、空格、标点，不使用模糊语义缓存。BiliBot 与 LivingMemory 对同一
事件生成不同正文时仍分别计算。缓存文本不会自动成为长期记忆。

缓存仅保存输入哈希、向量和时间，不保存请求正文或凭据。保存原始浮点精度，
与记忆库、FAISS、原子及图谱表分离；上限 10000 条，默认有效期 90 天。
另保留最多 256 条内存缓存，避免磁盘暂时写入失败后立即重复计算已付费向量。
`revision` 变化只隔离缓存，不能保证已存向量与真实更换后的模型空间兼容。

并发相同输入合并，未命中项每批最多 10 条，默认上游并发 2，待计算输入最多 256 条。
HTTP 请求取消不会取消已开始的共享计算；成功批次立即保存，后续批次失败不重算
已成功的批次。上游错误不缓存、不自动重试，调用方遵守退避策略。
缓存冷启动只按需求填充，不自动扫描或重建全部记忆。

`usage.prompt_tokens` 与 `usage.total_tokens` 表示当前请求实际发起的上游
计算消耗，完全命中时为 0；并发等待者不重复计量。这不同于原始输入的理论 tokens。
`X-Embedding-Cache` 提供命中、未命中与并发合并条数。
`GET /metrics` 需要同一令牌，输出启动以来的计量及调用方分组；SQLite
`usage_totals` 另保存成功缓存批次的累计上游请求、输入条数和实际 tokens。
客户端取消时以服务端累计计量为准，不把未知失败或网络超时计为免费。

`GET /health` 为本机健康检查。缓存或接口故障返回错误，保留调用方现有的
检索降级；不自动让所有调用方绕过缓存并放大上游请求。
缓存条目损坏或到期只重算相关输入。模型、账号或地域变化需要重载以建立新命名空间。

## 保留的服务器补丁

1. 空用户查询从 warning 改为 debug，避免工具轮次无正文时刷屏。
2. 记忆类型筛选使用 FACTUAL/EPISODIC，移除重复的 FACT/EVENT 别名选项。

发布只包含源码和上游离线前端产物；服务器安装目录中的 `data/`、凭据、
SQLite 文件、备份文件和 `node_modules/` 不进入 Git。

## 升级和回滚

先备份服务器插件代码、LivingMemory 配置、BiliBot 配置和所有 LivingMemory
数据（含 WAL）；发布前比较线上基线，存在新增补丁就停止覆盖。
停止 AstrBot 后再次执行一致性备份，安装测试通过的源码。
先启用 LivingMemory 缓存并验证健康、索引数量、提供商指纹，之后再将 BiliBot
的 `EMBED_API_BASE` 和 `EMBED_API_KEY` 指向本机接口及本机令牌。

验证同一文本从原生提供商与 OpenAI 接口分别访问，只产生一次上游请求。
确认老向量可检索、图谱仍可读、没有启动全量重建。
失败时恢复代码与配置，保留原数据；数据发生不兼容变化才使用停机一致性
数据备份回滚，不能覆盖发布后新增记忆而不说明损失。

源码管理保留官方上游 remote，使用 fork 的服务器维护分支。每次部署记录
上游提交、fork 提交、测试结果和回滚位置，避免回到旧安装包覆盖模式。
